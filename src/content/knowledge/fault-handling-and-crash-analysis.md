A production batch of industrial sensor nodes had been running flawlessly on the bench for six weeks. Three days after deployment in the field, units began resetting spontaneously.

This is the nature of hard faults on Cortex-M. They are not vague.

## The Cortex-M Fault Hierarchy

The Cortex-M architecture defines a hierarchy of fault exceptions, each targeting a different class of error. At the top sits HardFault, which is always enabled and cannot be disabled.

MemManage faults are generated by the Memory Protection Unit (MPU). If firmware attempts to access a memory region that the MPU has marked as privileged-only while executing in unprivileged mode, or attempts to execute from a region marked execute-never (XN), or writes to a read-only region, a MemManage fault fires.

## Fault Status Registers

ARM defines a set of registers in the System Control Block (SCB) that capture the cause and address of a fault at the moment it occurs. These registers are memory-mapped into the Private Peripheral Bus (PPB) region starting at 0xE000E000 and are accessible to privileged software at any time.

The Configurable Fault Status Register (CFSR) lives at address 0xE000ED28 and is 32 bits wide. It is subdivided into three fields: the MemManage Fault Status Register (MMFSR) occupies bits [7:0], the BusFault Status Register (BFSR) occupies bits [15:8], and the UsageFault Status Register (UFSR) occupies bits [31:16].

## Decoding the CFSR

The CFSR bit field is dense but unambiguous. Breaking it apart by sub-register makes it tractable.

Within the MemManage Fault Status Register (MMFSR, bits [7:0] of CFSR), IACCVIOL (bit 0, value 0x00000001) indicates an instruction access violation where the CPU tried to fetch an instruction from a region the MPU has marked as non-executable or privileged-only. DACCVIOL (bit 1, value 0x00000002) indicates a data access violation where a read or write was attempted to a region the MPU has disallowed.

## The Exception Stack Frame

When any exception fires on Cortex-M, the hardware automatically pushes a fixed set of registers onto the active stack before jumping to the exception handler. This automatic state save is what allows the fault handler to inspect the pre-fault machine state without any additional assembly code.

The stacked PC is the most immediately useful field. It is the address of the instruction the processor was about to execute when the fault was taken.

## Writing a Hard Fault Handler

A useful fault handler has three responsibilities: capture the stacked frame before anything can corrupt it, read the fault status registers before a secondary fault can clear them, and record everything to a location that survives the reset that will follow. The handler begins in assembly because C cannot reliably access the stack pointer before the C function prologue potentially modifies it.

The assembly trampoline is minimal. On entry to HardFault_Handler, the handler determines which stack was in use by examining bit 2 of the EXC_RETURN value held in LR.

## Common Fault Scenarios

Null pointer dereference is the most frequent source of HardFaults on Cortex-M. When a pointer holds the value NULL (0x00000000) and code attempts to read or write through it, the CPU issues a bus transaction to address 0x00000000.

Unaligned access faults fire when UNALIGN_TRP is set in CCR and firmware performs a word or halfword access to a non-aligned address. By default, Cortex-M3/M4 supports unaligned access transparently through hardware splitting, so this fault only fires when you explicitly enable the trap.

## Using a Debugger to Diagnose Faults

When a JTAG or SWD probe is attached and the firmware halts in the fault handler (or a breakpoint is set on HardFault_Handler), the debugger gives direct access to all the information needed for diagnosis. In STM32CubeIDE, the Fault Analyzer view is the fastest entry point: it reads SCB->CFSR, SCB->HFSR, and the stacked frame automatically and presents a decoded summary showing which bits are set and what they mean in plain language.

In GDB, the equivalent is performed manually. At the fault handler breakpoint, use "info registers" to see the current register state, then determine whether the stacked frame was on MSP or PSP by inspecting the LR value (EXC_RETURN).

## Fault Injection for Testing

Writing a fault handler is not sufficient; the handler itself must be tested. Fault injection means deliberately triggering each class of fault in a controlled test build to verify that the handler fires, captures correct data, and produces a correctly formatted log entry.

For UNDEFINSTR, embed an undefined Thumb instruction encoding using inline assembly: __asm volatile(".short 0xDE00"); produces a permanently undefined 16-bit encoding defined by the ARMv7-M architecture. For DIVBYZERO, set DIV_0_TRP in CCR (bit 4 at 0xE000ED14) and then execute a signed integer divide by zero using a volatile zero divisor to prevent the compiler from optimizing it away.

## Persistent Fault Logging

A fault that occurs in the field and resets the chip leaves no trace unless the firmware is designed to preserve fault information across the reset. The tools available depend on the hardware, but the most common approaches are retained RAM (a region of SRAM backed by the always-on power domain that survives a soft reset), internal flash, and external EEPROM or serial NOR flash.

The retained RAM approach is the fastest and requires no flash write cycles. On STM32 devices, the backup SRAM (BKPSRAM) is in the backup power domain and is preserved through system resets if VBAT is present.

## The MPU As a Fault Source

The Memory Protection Unit is both a source of MemManage faults and a powerful tool for converting latent memory corruption bugs into early, clean, diagnosable faults. When the MPU is configured with a region that covers the bottom guard page of a task stack as no-access, any stack overflow that crosses into that region immediately generates a MemManage fault rather than silently corrupting adjacent memory.

An effective MPU strategy for fault detection uses at minimum one no-access guard region below each task stack, a no-access region over the low addresses of the memory map to catch NULL pointer dereferences, and an execute-never (XN) attribute on all RAM regions where executable code is not intended to reside. The Cortex-M3/M4 MPU supports eight independently configurable regions with base-address and size constraints (size must be a power of two, minimum 32 bytes, base aligned to size).

## Key Takeaways

Enable the configurable fault exceptions at startup by setting USGFAULTENA, BUSFAULTENA, and MEMFAULTENA in SCB->SHCSR (0xE000ED24). Without these, all faults escalate to HardFault and you lose the per-type granularity the architecture provides, making every fault harder to classify at a glance.

Read CFSR, HFSR, BFAR, and MMFAR as the absolute first operation in your fault handler, using volatile reads, before any C call that could trigger a secondary fault and overwrite the valid-bit qualified address registers.
